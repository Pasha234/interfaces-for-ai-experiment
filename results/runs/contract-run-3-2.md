### 1. **SRP — принцип единственной ответственности (4 нарушения, было 3)**

- `postgres.BookingRepository` совмещает миграцию схемы и операции с бронированиями. Изменения в развёртывании базы затрагивают тот же тип, который обслуживает запросы приложения.
- `postgres.BookingRepository.List` выполняет выборку и определяет, какие бронирования считаются актуальными, через `end_time > now()`. Изменение этого правила требует правки адаптера хранения.
- Модуль `service` содержит правила бронирования и реализацию генерации UUID v4 в `newID`. Формат идентификатора и правила бронирования меняются по независимым причинам, но оба изменения затрагивают один модуль.
- `Handler.bookingByID` теперь распределяет запросы между `DELETE` и `PATCH` и сам формирует результат отмены. Изменение ответа на отмену затрагивает функцию, которая также маршрутизирует перенос.

### 2. **OCP — принцип открытости и закрытости (6 нарушений, было 4)**

- `Handler.bookings` вручную задаёт заголовок `Allow`. Добавление `HEAD /bookings` потребует обновить существующий ответ `405`, даже если зарегистрировать новый метод отдельно.
- `Handler.bookingByID` отдельно фиксирует набор разрешённых методов. Добавление `PATCH` уже потребовало правок и в маршрутизации, и в заголовке `Allow` этого обработчика. Для `GET /bookings/{id}` потребуется то же самое.
- `Handler.writeServiceError` сопоставляет конкретные доменные ошибки со статусами HTTP. Если запретить отмену начавшегося бронирования, для ответа `409` придётся менять общий преобразователь ошибок, который сейчас вернёт `500`.
- `BookingService.List` и `domain.BookingRepository.List` принимают только идентификатор комнаты, а SQL всегда исключает завершённые бронирования. Для режима просмотра истории в существующем списке придётся расширить оба контракта и изменить запрос.
- `domain.BookingRepository`, `domain.BookingService` и `httpapi.bookingService` расширили для переноса, хотя прежние операции остались прежними. Расширение сделало новый метод обязательным для каждой реализации этих интерфейсов, включая реализации, которым нужны только прежние операции.
- `BookingService.Create` и `BookingService.Reschedule` отдельно проверяют границы интервала. Введение общей минимальной длительности потребует изменить обе функции, иначе создание и перенос будут применять разные правила.

### 3. **LSP — принцип подстановки Барбары Лисков (2 нарушения, было 2)**

- `postgres.BookingRepository.Create` и `UpdateTimeRange` получают интервалы, прошедшие проверку сервиса, но `TIMESTAMPTZ` хранит границы с точностью до микросекунды. Если обе границы округлятся до одного значения, создание и перенос вернут HTTP `500`.
- `postgres.BookingRepository.Create`, `List`, `Delete` и `UpdateTimeRange` получают идентификаторы, в которых сервис допускает символ NUL. PostgreSQL отклоняет такой ввод для `TEXT`, поэтому создание, фильтрация, отмена и теперь перенос могут вернуть HTTP `500`.

### 4. **ISP — принцип разделения интерфейсов (0 нарушений, было 0)**
