Проверены исходники, интерфейсы, их реализации и места использования. Подтверждено одно нарушение; оценка процентов — экспертная, поскольку у SOLID нет формальной шкалы.

1. **SRP — принцип единственной ответственности (0 нарушений)**  
   Обязанности разделены по слоям: HTTP-обработчик обслуживает запросы, сервис выполняет сценарии бронирования, репозиторий отвечает за хранение. В просмотренном коде не нашлось модуля с обязанностями, меняющимися по явно независимым причинам.

2. **OCP — принцип открытости и закрытости (1 нарушение)**  
   При добавлении новой доменной ошибки с отдельным HTTP-ответом потребуется изменить `writeDomainError`: в ней вручную сопоставляются известные ошибки и статусы. Без этого новая ошибка попадёт в ответ по умолчанию с кодом 500.

3. **LSP — принцип подстановки Барбары Лисков (0 подтверждённых нарушений)**  
   Нарушений поведения контрактов не обнаружено. У каждого интерфейса видна только одна реализация, поэтому проверить взаимозаменяемость разных реализаций по текущему коду нельзя.

4. **ISP — принцип разделения интерфейсов (0 нарушений)**  
   `BookingService` использует все методы `BookingRepository`, а HTTP-обработчик — все методы `BookingService`. Признаков того, что потребитель вынужден зависеть от неиспользуемых методов, нет.

5. **DIP — принцип инверсии зависимостей (0 нарушений)**  
   Сервис зависит от интерфейса репозитория, а HTTP-обработчик — от интерфейса сервиса. Конкретный PostgreSQL-репозиторий подключается в точке сборки приложения.

**Оценка соответствия SOLID: 95%.**
