### 1. **SRP — принцип единственной ответственности (4 нарушения, было 3)**

- `Store.Create` разбирает HTTP-запрос, проверяет правила бронирования и управляет транзакцией PostgreSQL. Формат запроса, правила пересечения и механизм блокировки меняются в одной функции.
- `Store.List` разбирает HTTP-параметры, строит SQL-запрос и формирует JSON-ответ. Изменения формата выдачи и способа выборки затрагивают один обработчик.
- `Store.Cancel` проверяет идентификатор, обновляет запись и определяет HTTP-статус по числу изменённых строк. Изменение способа хранения отмены затрагивает HTTP-обработчик.
- `Store.Reschedule` разбирает запрос, проверяет новый интервал и выполняет транзакцию с блокировками. Изменения формата запроса, правил переноса и механизма блокировки затрагивают одну функцию.

### 2. **OCP — принцип открытости и закрытости (4 нарушения, было 3)**

- `Store.Create` и `Store.Reschedule` задают правило пересечения интервалов в отдельных SQL-запросах. Чтобы ввести обязательный перерыв между бронями для отдельных комнат, придётся менять обе проверки.
- `Store.Create` и `Store.Reschedule` отдельно разбирают даты через `time.Parse` с форматом RFC3339. Поддержка дополнительного формата ввода потребует изменить оба обработчика.
- `Store.List` добавляет фильтр по комнате при построении SQL. Чтобы добавить фильтр по периоду, придётся менять и разбор параметров, и построение запроса внутри `List`.
- `NewStore` принимает `*sql.DB`, а все четыре обработчика выполняют SQL напрямую. Чтобы добавить хранилище в памяти и сохранить существующий HTTP API, придётся менять обработчики и их подключение в `main`.

### 3. **LSP — принцип подстановки Барбары Лисков (0 подтверждённых нарушений, было 0)**

`logging` передаёт запрос и объект ответа вложенному `http.Handler`. Для хранения броней по-прежнему есть один конкретный `Store`, поэтому взаимозаменяемость хранилищ по допустимым входным данным и ожидаемым ошибкам проверить нельзя.

### 4. **ISP — принцип разделения интерфейсов (0 нарушений, было 0)**

`logging` использует единственный метод интерфейса `http.Handler`. Каждый маршрут, включая новый `PATCH`, получает через `HandleFunc` только свой обработчик.

### 5. **DIP — принцип инверсии зависимостей (4 нарушения, было 3)**

- `Store.Create` напрямую использует SQL-транзакцию и блокировку PostgreSQL. Чтобы проверить обработку конфликта с подставным хранилищем, пришлось бы имитировать SQL-операции.
- `Store.List` вызывает `QueryContext` и считывает строки SQL-результата. Подмена источника списка требует имитации SQL-слоя.
- `Store.Cancel` определяет результат отмены через `sql.Result.RowsAffected`. Выбор HTTP-статуса зависит от того, как драйвер сообщает о результате обновления.
- `Store.Reschedule` выбирает `404` по `sql.ErrNoRows` и сам управляет блокировками PostgreSQL. Проверка сценариев переноса через подставное хранилище требует воспроизвести поведение SQL-транзакции.
