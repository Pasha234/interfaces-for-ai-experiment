Проверил исходники всего проекта, реализации интерфейсов и их вызовы. `go test ./...` и `go vet ./...` прошли. Тестов в проекте нет, поэтому поведение с PostgreSQL оценивал по коду и ограничениям используемых типов.

### 1. **SRP — принцип единственной ответственности (3 нарушения)**

- `postgres.BookingRepository` выполняет и миграцию схемы, и операции с бронированиями. Изменение порядка развёртывания базы затрагивает тот же тип, что и повседневная работа с данными.
- `postgres.BookingRepository.List` выполняет выборку и сам определяет, какие бронирования считать актуальными, через `end_time > now()`. Изменение этого правила требует правки адаптера хранения.
- Модуль `service` реализует правила бронирования и низкоуровневую генерацию UUID v4 в `newID`. Формат идентификатора можно менять независимо от правил бронирования, но оба изменения затрагивают один модуль.

### 2. **OCP — принцип открытости и закрытости (4 нарушения)**

- `Handler.bookings` вручную задаёт список разрешённых методов в `Allow`. Добавление `HEAD /bookings` потребует обновить существующий обработчик ответа `405`, даже если новый метод зарегистрировать отдельно.
- `Handler.bookingByID` отдельно фиксирует `Allow: DELETE`. Добавление `GET /bookings/{id}` потребует исправить этот ответ, иначе он продолжит объявлять только `DELETE`.
- `Handler.writeServiceError` сопоставляет конкретные доменные ошибки со статусами HTTP. Чтобы запрет отмены уже начавшегося бронирования возвращал `409`, придётся менять общий преобразователь ошибок, который сейчас вернёт `500`.
- `BookingService.List` и `domain.BookingRepository.List` позволяют передать только комнату, а SQL всегда исключает завершённые бронирования. Чтобы добавить режим просмотра истории в существующий сценарий списка, придётся расширить оба контракта и изменить запрос.

### 3. **LSP — принцип подстановки Барбары Лисков (2 нарушения)**

- `postgres.BookingRepository.Create` принимает уже проверенный сервисом интервал, но `TIMESTAMPTZ` хранит время с точностью до микросекунды. Границы короткого интервала могут округлиться до одного значения, и тогда PostgreSQL отклонит запись, а API вернёт `500`. [Документация PostgreSQL о точности времени](https://www.postgresql.org/docs/18/datatype-datetime.html)
- `postgres.BookingRepository.Create`, `List` и `Delete` получают строковые идентификаторы, для которых сервис допускает символ NUL. PostgreSQL отклоняет такие значения в параметрах типа `TEXT`, поэтому создание, фильтрация и отмена могут завершиться HTTP `500`. [Документация PostgreSQL о текстовых типах](https://www.postgresql.org/docs/18/datatype-character.html)

### 4. **ISP — принцип разделения интерфейсов (0 нарушений)**

- `Handler` использует все методы `bookingService`, а `service.BookingService` — все методы `domain.BookingRepository`. У `domain.BookingService` есть проверка реализации при компиляции, а потребителей в проекте нет.

### 5. **DIP — принцип инверсии зависимостей (1 нарушение)**

- `service.BookingService.Create` напрямую вызывает `newID`, который использует `crypto/rand` и вручную формирует UUID v4. Подставить предсказуемый генератор для проверки сценария или сменить способ выдачи идентификаторов можно только через изменение пакета сервиса.

**Итоговое соответствие SOLID — 70%.** Это оценка по условной шкале из 20 баллов на принцип со штрафом в 3 балла за каждое подтверждённое нарушение.
