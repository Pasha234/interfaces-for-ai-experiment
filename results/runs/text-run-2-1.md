1. **SRP — принцип единственной ответственности (4 нарушения)**

   - `server.createBooking` разбирает HTTP-запрос, проверяет правила бронирования и управляет транзакцией PostgreSQL. Изменения формата запроса, бизнес-правил и механизма блокировки затрагивают один обработчик.
   - `server.listBookings` совмещает разбор HTTP-фильтра, построение SQL-запроса, чтение строк и формирование JSON-ответа. Формат API и способ выборки меняются в одной функции.
   - `server.bookingByID` разбирает маршрут, выполняет отмену через SQL и преобразует число затронутых строк в HTTP-статус. Изменение способа отмены затрагивает обработчик маршрута.
   - `booking` используется как входная модель, модель чтения из БД и JSON-ответ. В результате запрос принимает поле `id`, которое `server.createBooking` перезаписывает, а изменение полей ответа может изменить и формат входных данных.

2. **OCP — принцип открытости и закрытости (3 нарушения)**

   - `server.bookings` вручную распределяет методы для `/bookings`. Чтобы добавить `HEAD`, придётся изменить ветвление и отдельно обновить заголовок `Allow`.
   - `server.bookingByID` пропускает только `DELETE`. Чтобы добавить `GET /bookings/{id}`, придётся изменить действующий обработчик отмены и его заголовок `Allow`.
   - `server.createBooking`, `server.listBookings` и `server.bookingByID` независимо определяют активность записи через `cancelled_at IS NULL`. Добавление временной брони, которая истекает автоматически, потребует изменить все три SQL-запроса, чтобы проверка доступности, выдача списка и отмена одинаково трактовали истёкшие записи.

3. **LSP — принцип подстановки Барбары Лисков (0 подтверждённых нарушений)**

   - В проекте нет собственных интерфейсов со взаимозаменяемыми реализациями. По текущему коду нельзя проверить, сохранятся ли допустимые входы и ожидаемые ошибки при замене реализации хранилища.

4. **ISP — принцип разделения интерфейсов (0 нарушений)**

   - Собственных интерфейсов в проекте нет. Обработчики используют все операции стандартного `http.ResponseWriter` через установку заголовков, отправку статуса и запись тела ответа.

5. **DIP — принцип инверсии зависимостей (3 нарушения)**

   - `server.createBooking` напрямую управляет `*sql.Tx` и вызывает `pg_advisory_xact_lock`. Замена хранилища или механизма обеспечения атомарности требует переписать сценарий создания брони.
   - `server.listBookings` напрямую вызывает `*sql.DB.QueryContext` и считывает строки через `Scan`. Замена источника данных требует менять HTTP-обработчик списка.
   - `server.bookingByID` напрямую выполняет SQL-обновление и использует `RowsAffected`, чтобы определить результат отмены. При замене хранилища меняется и код, который выбирает HTTP-статус.
