### 1. **SRP — принцип единственной ответственности (3 нарушения)**

- `Store.Create` разбирает HTTP-запрос, проверяет правила бронирования и управляет транзакцией PostgreSQL. Изменение формата запроса, правил пересечения или механизма блокировки затрагивает один обработчик.
- `Store.List` разбирает HTTP-параметры, формирует SQL-запрос и сериализует ответ. Формат выдачи и способ выборки активных броней меняются в одной функции.
- `Store.Cancel` проверяет идентификатор, выполняет отмену через `UPDATE` и выбирает HTTP-статус по числу изменённых строк. Изменение представления отмены в базе затрагивает обработчик HTTP.

### 2. **OCP — принцип открытости и закрытости (3 нарушения)**

- `Store.Create` задаёт правило пересечения интервалов внутри SQL-запроса. Чтобы ввести обязательный перерыв между бронями для отдельных комнат, придётся менять существующую проверку конфликта.
- `Store.List` добавляет фильтр по комнате непосредственно при сборке SQL. Чтобы добавить фильтрацию по периоду, придётся менять в `List` и разбор параметров, и построение запроса.
- `NewStore` принимает только `*sql.DB`, а `Migrate` и `Store.Create` содержат конструкции PostgreSQL. Чтобы добавить хранилище в памяти, придётся изменить регистрацию обработчиков в `main` и вынести операции хранения из `Create`, `List` и `Cancel`.

### 3. **LSP — принцип подстановки Барбары Лисков (0 подтверждённых нарушений)**

Контракт `http.Handler` соблюдается в проверенных местах использования. Для хранения броней есть один конкретный `Store` и отсутствует общий контракт, по которому можно проверить взаимозаменяемость реализаций, включая допустимые входные данные и ожидаемые ошибки.

### 4. **ISP — принцип разделения интерфейсов (0 нарушений)**

`logging` использует единственный метод `http.Handler`. Маршруты получают отдельные функции через `HandleFunc`, поэтому ни один маршрут не зависит от остальных операций `Store`.

### 5. **DIP — принцип инверсии зависимостей (3 нарушения)**

- `Store.Create` реализует создание брони через `*sql.DB`, SQL-транзакцию и блокировку PostgreSQL. Проверить сценарий успешной записи или конфликта через подставное хранилище на уровне операции бронирования нельзя.
- `Store.List` напрямую вызывает `QueryContext` и считывает строки SQL-результата. Чтобы проверить выдачу списка с подставными данными, нужно имитировать поведение SQL-слоя.
- `Store.Cancel` определяет результат отмены через `sql.Result.RowsAffected`. Обработчик зависит от того, как SQL-драйвер сообщает о результате обновления.

**Итоговая оценка соответствия SOLID — 25%.** Каждый полностью оценённый принцип имеет одинаковый вес. Из четырёх таких принципов только ISP прошёл без нарушений. LSP исключён из расчёта, поскольку взаимозаменяемость хранилищ нельзя проверить по текущему коду.
